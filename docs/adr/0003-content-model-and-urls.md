# 文章与作品各自建表，地址首次发布即冻结

文章与作品分成 `Article`、`Project` 两张表，共用 `status` 枚举（`DRAFT` / `PUBLISHED` / `WITHDRAWN`）。标签独立建表，与文章多对多。作品的类型用字符串（后台固定下拉选项），改词不用迁移。

首页排序用主表上的 `featuredRank Int?`：为空表示未入选，值决定顺序，后台校验文章最多 5 篇、作品最多 3 件。撤下只改 `status`，不动 `featuredRank`，所以再次发布能恢复原来的精选位置。

首页 Hero 介绍、主要联系地址与有序社交链接保存在单条 `SiteSetting` 记录中，供中英文界面共用并保留录入原文。站点设置不承载精选文章或首页作品的排序；排序仍分别保存在 `Article` 与 `Project` 主表。

`slug` 在首次发布时生成后冻结，地址形如 `/articles/<slug>`、`/projects/<slug>`；标题改动不影响链接，因此不需要重定向表。`firstPublishedAt` 同样在首次发布时写入、此后不变，列表按它倒序。搜索用的归一化纯文本列 `searchText` 在发布时生成落库——中文连续词组匹配需要它（见 issue #25 的调研）。

## 考虑过的替代方案

- **单表 `Content` + `kind`**：两边的字段分叉很大（作品有类型、卡片主入口、外部地址；文章有摘要、标签），合并后一半字段恒为空，且「只有站内详情才需要正文语言」这类约束难以表达。
- **独立 `HomeConfig` 表**：多一张表与一次关联查询，换不来灵活性。
- **允许随时改 slug + 重定向表**：是为「允许改」付的长期成本，而需求只要求地址稳定。
- **用 `cuid` 作路径**：不可读；也不解决中文标题转写问题（转写要引入拼音库且歧义多）。

## 后果

首次发布是不可回退的一刻：slug 与 `firstPublishedAt` 都在此刻确定。后台需要在发布前让站长确认 slug。
